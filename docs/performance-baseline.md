# Performance baseline

Эталонные значения Core Web Vitals для https://meetly.linnetlab.com/.
С ними ночной аудит (`.github/workflows/opencode-lighthouse.yml`) сравнивает
свежие замеры и решает, заводить ли issue.

Замер снят **26 августа 2026** на раннере GitHub Actions, Lighthouse 12.8.2
([run 33001168508](https://github.com/aramis2019/ai-for-developers-project-387/actions/runs/33001168508)).

## Методика

Цифры имеют смысл только вместе с условиями замера — метрики, снятые при
разных настройках троттлинга или на другом железе, несравнимы.

| Параметр | Значение |
| --- | --- |
| Инструмент | Lighthouse CLI 12.x, `--only-categories=performance` |
| Форм-фактор | `mobile` (дефолт Lighthouse) |
| Троттлинг | `simulate`, CPU ×4, RTT 150 мс, 1638.4 Кбит/с |
| Прогонов на страницу | 3, берётся **медиана** |
| Окружение | GitHub Actions `ubuntu-latest`, headless Chrome |

Baseline снимается **только на раннере GitHub Actions**. Замер с ноутбука
разработчика для сравнения не годится: на локальной машине те же страницы
дали Speed Index 4510 мс против 5217 мс на раннере — расхождение 16%,
которое целиком объясняется разницей в железе, а не в приложении.

### Почему медиана и почему минимум три прогона

Первый прогон в задаче систематически даёт выброс: Chrome стартует
вхолодную, `npx` тянет пакет. Замеренное на CI:

| Страница | TBT по прогонам | Медиана |
| --- | --- | --- |
| `/` | **310** / 45 / 43 | 45 |
| `/book/intro-call` | **373** / 115 / 130 | 130 |

Медиана из трёх отбрасывает выброс. При `runs=1` в отчёт попадает ровно этот
холодный прогон, и метрика завышается в 5–7 раз. При `runs=2` медиана
усредняет выброс со здоровым значением и тоже врёт.

Отсюда правило: **сравнивать с baseline можно только замеры с `runs` ≥ 3
и нечётным**. Меньшие значения допустимы лишь для отладки самого workflow,
когда важно, что задача проходит, а не какие в ней цифры.

Остальные метрики устойчивы: FCP и LCP держатся в пределах 1.5% между
прогонами, CLS стабильно нулевой.

## Почему TBT, а не INP

INP измеряется по реальным взаимодействиям пользователя и в lab-режиме
недоступен: Lighthouse не кликает по странице. Стандартный лабораторный
прокси для INP — **Total Blocking Time**, он же показывает, насколько долго
главный поток занят и не отвечает на ввод.

Настоящий INP собирается только с живого трафика (CrUX, RUM). Для
meetly.linnetlab.com данных в CrUX нет — домен не набирает нужный объём
трафика. Поэтому в baseline TBT, и в отчётах его нельзя называть INP.

## Пороги срабатывания

Наивное «хуже на 10%» здесь не работает по двум причинам:

- **CLS = 0.** Десять процентов от нуля — ноль, любое ненулевое значение
  считалось бы регрессией. Нужен абсолютный порог.
- **TBT шумит в разы.** Порог 10% давал бы ложную тревогу почти каждую ночь.

Поэтому для шумных метрик регрессия засчитывается, только когда превышены
**оба** порога — относительный и абсолютный:

| Метрика | Относительный | Абсолютный | Условие |
| --- | --- | --- | --- |
| LCP | +10% | +200 мс | оба |
| FCP | +10% | +200 мс | оба |
| Speed Index | +10% | +200 мс | оба |
| TBT | +10% | +50 мс | оба |
| CLS | — | > 0.02 | только абсолютный |
| Performance score | — | −5 пунктов | только абсолютный |

Абсолютный порог TBT в 50 мс выбран по замеренному шуму. На здоровых
прогонах (без холодного старта) TBT гуляет на 43–45 мс на главной и
115–130 мс на странице записи; порог ниже 50 мс ловил бы это дрожание,
а не регрессию.

## Как обновить baseline

После осознанной оптимизации или изменения, которое закономерно двигает
метрики, цифры пересчитываются, а не подгоняются под факт.

1. Actions → **opencode: lighthouse** → Run workflow, `runs` = 3,
   `dry_run` = true. Локально не замерять: цифры с ноутбука несравнимы
   с раннером.
2. Скачать артефакт `lighthouse-reports` — в нём уже лежит готовый
   `lighthouse-summary.json` с медианами.
3. Перенести медианы в таблицы выше, обновить дату замера и ссылку на run.

Пересчитать сводку из сырых отчётов вручную, если это нужно:

```bash
node .github/scripts/lighthouse-summary.mjs ./reports ./summary.json
```

Обновление baseline — отдельный коммит с обоснованием в сообщении: что
изменилось в приложении и почему новые цифры считаются нормой.
